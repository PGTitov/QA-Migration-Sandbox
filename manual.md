# Manual QA to Web Automation QAE

## Практичний посібник із Playwright

Цей посібник призначений для Manual QA інженера, який переходить до веб-автоматизації на TypeScript і Playwright. Навчання проходить послідовно: спочатку базові знання та налаштування, потім Junior-рівень, після цього Middle-рівень.

Мета посібника - не просто отримати тести, що проходять, а навчитися пояснювати код, обирати стабільні локатори, створювати змістовні перевірки, знаходити причини помилок і підтримувати проєкт.

> Виконання всіх завдань саме по собі не означає автоматичне підвищення. Результат оцінює наставник або SME за кодом, тестами, доказами та рівнем самостійності.

## Швидке пояснення автоматизації

Автоматизований тест - це програма, яка повторює дії користувача та перевіряє результат.

```text
підготувати стан -> виконати дію -> перевірити результат
```

Наприклад:

```ts
await page.goto('/text-box');                         // підготовка
await page.getByLabel('Full Name').fill('John Doe');  // дія
await page.getByRole('button', { name: 'Submit' }).click();
await expect(page.getByText('John Doe')).toBeVisible(); // перевірка
```

Хороший тест відповідає на чотири питання:

1. У якому стані починається сценарій?
2. Яку дію виконує користувач?
3. Який результат очікується?
4. Чому цей результат важливий?

### Що таке evidence package

`Evidence package` - це набір матеріалів, за якими наставник може перевірити не лише факт виконання, а й розуміння роботи.

Зазвичай він містить:

- код тестів і пов'язаних page objects;
- команду запуску та результат виконання;
- screenshot, video або trace для прикладу debugging;
- опис локаторів, assertions і тестових даних;
- пояснення проблеми, рішення та альтернатив;
- Git-гілку з читабельними комітами;
- AI-assisted note: що було прийнято, відхилено і перевірено.

Evidence package має показати зв'язок: **завдання -> реалізація -> перевірка -> пояснення**.

### Що означає «учень розуміє»

Учень розуміє тему, якщо може власними словами пояснити:

- що робить код;
- чому вибрано саме такий locator;
- що перевіряє assertion;
- що станеться при помилці;
- де змінити код при зміні вимоги.

## Як працювати з посібником

Для кожного етапу потрібно:

1. Прочитати мету та очікуваний результат.
2. Виконати практичні завдання в цьому репозиторії.
3. Запустити тести та перевірити результат.
4. Записати, що було зроблено і чому саме так.
5. Зібрати докази для перевірки.

Рекомендований цикл навчання:

```text
зрозуміти -> запустити -> змінити -> створити -> переробити -> стабілізувати
```

## Проєкт і відповідальність шарів

У цьому репозиторії використовуються такі шари:

- `tests/` - сценарії та перевірки користувацької поведінки;
- `page-model/` - page objects, локатори та дії для конкретних сторінок;
- `page-model/controls/` - повторно використовувані контролі, наприклад кнопки або поля;
- `tests/fixtures.ts` - спільний тестовий контекст і fixture `demoQA`;
- `data/` - тестові дані без логіки поведінки;
- `utils/` - технічні допоміжні функції;
- `config.ts` - базова URL-адреса та маршрути;
- `playwright.config.ts` - налаштування запуску Playwright.

Приклад розподілу відповідальності:

```text
Тест: що перевіряємо
Page object: як взаємодіємо зі сторінкою
Control: як працюємо з конкретним елементом
Fixture: який контекст готуємо
Test data: з якими значеннями працюємо
```

# Етап 0. Вхідні критерії Junior

## Мета

Перевірити, що учень має мінімальну базу для продуктивного навчання автоматизації.

## Обов'язкові знання

### Змінні

Змінна зберігає значення.

```ts
const email = 'user@example.com';
let attempts = 0;
attempts = attempts + 1;
```

`const` використовують, коли змінну не потрібно переприсвоювати. `let` використовують, коли значення змінюється.

### Функції

Функція об'єднує повторювану логіку.

```ts
function createGreeting(name: string): string {
  return `Hello, ${name}`;
}
```

У тестах функцією може бути окрема дія, наприклад `openLoginPage(page)`.

### Умови

Умова дозволяє виконати різний код залежно від ситуації.

```ts
if (isLoggedIn) {
  console.log('User is logged in');
} else {
  console.log('User is logged out');
}
```

### Цикли

Цикл повторює дію для набору даних.

```ts
for (const pageName of ['text-box', 'buttons', 'checkbox']) {
  console.log(pageName);
}
```

### Масиви та об'єкти

Масив - це список значень:

```ts
const browsers = ['chromium', 'firefox', 'webkit'];
```

Об'єкт містить пов'язані властивості:

```ts
const user = {
  name: 'Olena',
  email: 'olena@example.com',
};
```

### Базова обробка помилок

`try/catch` дозволяє обробити очікувану помилку:

```ts
try {
  await page.goto('/login');
} catch (error) {
  console.log('Page could not be opened');
}
```

У тестах не слід приховувати помилки без причини. Якщо дія не виконалась, краще побачити справжню причину падіння.

### Git

Потрібно вміти перевірити статус, створити гілку, зробити коміт і відправити зміни:

```text
git status
git switch -c test-automation
git add .
git commit -m "Add checkbox tests"
git push -u origin test-automation
```

### Командний рядок

Потрібно вміти перейти до папки та запустити команду:

```text
cd QA-Migration-Sandbox
dir
npm install
npm test
```

### Основи веб-тестування

- Навігація: користувач потрапив на правильну сторінку.
- Форма: дані введені та відправлені.
- Валідація: неправильні дані відхилені.
- Позитивний сценарій: правильні дані дають очікуваний результат.
- Негативний сценарій: помилкові або неповні дані обробляються коректно.

```ts
await page.goto('/text-box');
await page.getByLabel('Full Name').fill('John Doe');
await page.getByRole('button', { name: 'Submit' }).click();
await expect(page.getByText('John Doe')).toBeVisible();
```

## Корисні знання, які можна посилити далі

- `async/await` - очікування асинхронних дій браузера;
- імпорти та модулі - використання коду з інших файлів;
- npm - керування пакетами та командами;
- структура TypeScript/JavaScript-файлу - розуміння імпортів, функцій, класів і тестів.

## Перевірка готовності

Учень повинен власними словами пояснити:

- різницю між `let` і `const`;
- що робить проста функція;
- для чого потрібні базові команди термінала;
- як запустити команду проєкту за інструкцією.

Доказ: короткий self-check або невеликий JS/TS-приклад.

### Що очікується від учня

Учень не повинен знати весь TypeScript. Достатньо вміти прочитати простий приклад, передбачити його результат, змінити значення та пояснити основні конструкції. Наприклад, учень має пояснити, чому `attempts` оголошено через `let`, а `email` - через `const`.

### Evidence package етапу 0

- короткий self-check;
- невеликий JS/TS-приклад зі змінною, функцією, умовою та циклом;
- усне або письмове пояснення базових понять.

# Етап 2. Основи Playwright

## Мета

Навчитися писати прості, читабельні та стабільні UI-тести.

## Основні поняття

- `test()` - опис тестового сценарію;
- `expect()` - перевірка очікуваного результату;
- `page` - поточна сторінка браузера;
- `page.goto()` - навігація;
- `click()` - клік;
- `fill()` - введення тексту;
- locator - спосіб знайти елемент.

## Приклад

```ts
import { test, expect } from '@playwright/test';

test('user can submit text', async ({ page }) => {
  await page.goto('/text-box');
  await page.getByLabel('Full Name').fill('John Doe');
  await page.getByRole('button', { name: 'Submit' }).click();
  await expect(page.getByText('John Doe')).toBeVisible();
});
```

## Локатори

Рекомендований порядок:

1. `getByRole()` - елемент за роллю та доступною назвою;
2. `getByLabel()` - поле за підписом;
3. `getByText()` або `getByPlaceholder()`;
4. `getByTestId()` - коли user-facing locator недостатньо стабільний;
5. CSS/XPath - лише з поясненням причини.

Сильний локатор зрозумілий, стабільний і відповідає тому, що бачить користувач.

## Очікування

Playwright сам очікує, поки елемент стане доступним для дії. Не слід додавати `waitForTimeout()` без чіткої причини.

```ts
await page.getByRole('button', { name: 'Submit' }).click();
await expect(page.getByText('Success')).toBeVisible();
```

## Практика

Створити 3-5 тестів для таких дій:

- відкрити сторінку;
- перевірити title або URL;
- натиснути кнопку;
- заповнити форму;
- перевірити повідомлення або зміну стану.

Докази: код тестів, пояснення локаторів і пояснення assertions.

### Що потрібно розуміти

Учень має відрізняти дію від перевірки. `click()` виконує дію, а `expect()` підтверджує, що результат настав. Locator - це спосіб пошуку елемента.

```ts
page.getByRole('button', { name: 'Submit' })
```

Такий locator зрозуміліший і часто стабільніший за `.btn.btn-primary:nth-child(3)`, бо описує поведінку користувача, а не внутрішню HTML-структуру.

### Evidence package етапу 2

- 3-5 незалежних тестів;
- для кожного тесту: початковий стан, дія та очікуваний результат;
- приклади сильних locator-ів;
- позитивний і негативний сценарій;
- пояснення, чому не використано `waitForTimeout()`.

# Етап 3. Структурований проєкт

## Мета

Перейти від ізольованих тестів до проєкту з узгодженою структурою.

## Завдання

1. Розібрати структуру `tests`, `page-model`, `controls`, `fixtures`, `data` та `utils`.
2. Додавати тести у відповідну папку.
3. Використовувати наявні page objects і controls.
4. Виносити повторювані дії лише тоді, коли це покращує читабельність або повторне використання.
5. Розібрати один failure через screenshot, video або Trace Viewer.

## Приклад page object

```ts
export class TextBoxPage {
  async fillForm(name: string, email: string): Promise<void> {
    await this.fullNameField.fill(name);
    await this.emailField.fill(email);
  }
}
```

Тест описує сценарій, а page object приховує технічні локатори та дії сторінки.

## Межі шарів

- Page object містить поведінку конкретної сторінки.
- Helper містить спільну технічну логіку.
- Fixture готує спільний контекст.
- Test data містить значення, а не дії.

Докази: один доданий або оновлений тест, один приклад debugging і коротке пояснення структури.

### Що потрібно розуміти

- тест описує сценарій і бізнес-перевірку;
- page object містить locator-и та дії конкретної сторінки;
- helper містить спільну технічну дію;
- fixture готує спільний контекст;
- test data містить значення, а не поведінку.

Учень має вміти відкрити failure і перевірити assertion, locator, screenshot та trace.

### Evidence package етапу 3

- diff доданого або оновленого тесту;
- коротка схема відповідальності шарів;
- один failure analysis: симптом, причина, fix і повторний результат;
- команда, якою проблема була перевірена.

# Етап 4. Практичні Junior-сценарії

## Мета

Автоматизувати 2-3 зрозумілі багатокрокові сценарії з якісними assertions.

## Варіанти завдань

### Введення тексту та перевірка результату

Відкрити Text Box, заповнити поля, натиснути Submit і перевірити, що значення з'явилися у result area.

```ts
await demoQA.textBoxPage.fillForm('John Doe', 'john@example.com');
await demoQA.textBoxPage.submit();
await demoQA.textBoxPage.verify.outputContainsName('John Doe');
```

### Валідація форми

Ввести некоректний email і перевірити, що поле невалідне, а результат не створено.

```ts
await demoQA.textBoxPage.emailField.typeText('invalid-email');
await demoQA.textBoxPage.submit();
await demoQA.textBoxPage.verify.emailIsInvalid();
```

### Стан кнопки або опції

Натиснути кнопку, обрати radio button або checkbox і перевірити повідомлення чи selected state.

```ts
await demoQA.checkBoxPage.checkItem('Home');
await demoQA.checkBoxPage.verify.itemIsSelected('home');
```

### Таблиця

Додати або знайти запис у Web Tables і перевірити його значення.

### Навігація

Перейти за посиланням і перевірити URL, title або видимий контент цільової сторінки.

### Upload/download

Виконати операцію з файлом і перевірити видимий результат, наприклад ім'я завантаженого файла.

### Alert або modal

Викликати діалог, обробити його та перевірити фінальний стан сторінки.

## Критерії завершення

Учень може пояснити призначення сценарію, preconditions, обрані локатори, assertions і очікуваний результат.

### Що очікується від учня

Для кожного сценарію учень має пояснити:

- **Purpose** - яку поведінку перевіряємо;
- **Preconditions** - що підготовлено до першої дії;
- **Test data** - які значення використовуються і чому;
- **Locator strategy** - як знаходяться елементи;
- **Assertions** - який результат підтверджується;
- **Isolation** - чому тест запускається окремо;
- **Cleanup** - чи потрібно видалити створені дані.

### Evidence package етапу 4

- 2-3 практичні сценарії;
- код і результат запуску кожного сценарію;
- опис purpose, preconditions і assertions;
- позитивний і негативний шлях, якщо сторінка це дозволяє;
- пояснення одного рішення, зміненого після debugging.

- розділити дії, перевірки, setup і test data;
- уникати зайвої залежності між класами;
- пояснити, чому логіка належить саме цьому шару.

## Приклад рефакторингу

До рефакторингу:

```ts
await page.getByLabel('Full Name').fill(name);
await page.getByLabel('Email').fill(email);
await page.getByRole('button', { name: 'Submit' }).click();
```

Після рефакторингу в page object:

```ts
await demoQA.textBoxPage.fillForm(name, email);
await demoQA.textBoxPage.submit();
```

Абстракція виправдана, якщо вона прибирає повторення і залишає тест зрозумілим.

Доказ: before/after, пояснення покращення та компромісів.

### Що потрібно розуміти

На Middle-рівні недостатньо сказати «я виніс код у метод». Учень має пояснити, яку duplication усунуто, чому метод має саме таку відповідальність і який недолік може мати нова абстракція.

### Evidence package етапу 5

- before/after diff;
- опис проблеми до рефакторингу;
- пояснення обраної абстракції та альтернативи;
- успішний typecheck і запуск пов'язаних тестів.

# Етап 6. Middle: повторно використовувана структура

## Мета

Створювати корисні page objects, helpers, fixtures і reusable flows без overengineering.

## Завдання

- покращити один page object або component;
- додати reusable flow;
- створити helper, якщо він справді спільний;
- покращити fixture або shared setup;
- організувати test data;
- додати reusable authentication/prepared state, якщо це потрібно.

## Як перевірити якість абстракції

Абстракція корисна, якщо:

- повторюється в кількох тестах;
- має зрозумілу назву;
- приховує технічні деталі;
- не приховує важливу логіку сценарію.

Абстракція зайва, якщо вона використовується один раз або змушує читача переходити через багато файлів для розуміння простого кроку.

Докази: зміна page object/helper, приклад повторного використання та пояснення користі.

### Що потрібно розуміти

Reusable flow доречний, коли одна послідовність дій повторюється в кількох сценаріях і має зрозумілу назву, наприклад `createUser()` або `fillBasicInfo()`.

Fixture готує спільний контекст, а не приховує весь тестовий сценарій. Page object містить поведінку сторінки, а test data - значення без логіки.

### Evidence package етапу 6

- код page object, helper, fixture або flow;
- щонайменше два місця використання, якщо це reusable-логіка;
- before/after приклад duplication;
- пояснення, чому нова структура спрощує наступний тест.

# Етап 7. Middle: end-to-end і coverage thinking

## Мета

Самостійно проєктувати повні сценарії та пояснювати, яку цінність дає кожна перевірка.

## Завдання

Створити 3-5 сценаріїв, які можуть включати:

- create/edit flow;
- multi-step form;
- Web Tables: add, search, edit, delete;
- prepared-state flow;
- позитивний і негативний варіант;
- додаткову boundary або missing variation;
- API-assisted setup, якщо він реально покращує швидкість і стабільність.

Для кожного сценарію потрібно описати:

- preconditions;
- тестові дані;
- основні кроки;
- очікуваний результат;
- чому сценарій важливий;
- що залишається непокритим.

## Приклад coverage gap

Якщо перевіряється лише успішне заповнення email, корисним розширенням може бути перевірка порожнього або неправильного email. Це збільшує цінність suite, бо перевіряє захист від некоректних даних.

Докази: 3-5 E2E-сценаріїв, пояснення coverage та пропозиція наступних кандидатів для автоматизації.

### Що потрібно розуміти

Учень має відрізняти кількість тестів від якості coverage. П'ять схожих позитивних тестів не обов'язково корисніші за один позитивний, один негативний і один boundary-сценарій.

Для кожного coverage gap потрібно вказати, що вже перевірено, чого не перевірено, який ризик існує та чому новий тест має цінність.

### Evidence package етапу 7

- 3-5 повних E2E-сценаріїв;
- перелік позитивних, негативних і boundary-перевірок;
- коротка coverage matrix або список покритих ризиків;
- 2-3 обґрунтовані кандидати для наступної автоматизації.

# Етап 8. Middle: стабільність і debugging

## Мета

Знаходити та виправляти root cause flaky tests, а не маскувати проблему retries або hard waits.

## Порядок аналізу failure

1. Прочитати assertion message.
2. Перевірити правильність locator.
3. Відкрити trace.
4. Переглянути screenshot або video.
5. Перевірити network/request проблеми.
6. Перевірити test data та environment state.
7. Перевірити залежність від попереднього тесту.

## Типові причини нестабільності

- неправильний або технічний locator;
- дія відбувається до готовності сторінки;
- залишився state від іншого тесту;
- тестові дані конфліктують;
- зовнішнє середовище нестабільне;
- використано unnecessary hard wait.

## Приклад

Погане рішення:

```ts
await page.waitForTimeout(3000);
await page.getByText('Saved').click();
```

Краще рішення:

```ts
await expect(page.getByText('Saved')).toBeVisible();
await page.getByText('Saved').click();
```

Доказ: опис нестабільності, root cause, зміна, before/after результат і пояснення, чому нова версія надійніша.

### Що потрібно розуміти

Учень має розрізняти симптом і root cause. «Тест іноді не знаходить текст» - це симптом. Причиною може бути слабкий locator, неправильний стан даних або відсутність очікування потрібної зміни UI.

Retry може показати, що проблема тимчасова, але не доводить, що тест виправлено. Hard wait лише затримує виконання і не гарантує потрібного стану.

### Evidence package етапу 8

- назва нестабільного тесту та умови відтворення;
- assertion message, screenshot або trace;
- гіпотеза щодо root cause;
- конкретна зміна та результат повторного запуску;
- пояснення, чому retry або hard wait не є основним fix.

# Етап 9. Middle: configuration, fixtures і CI

## Мета

Впевнено працювати з execution context, конфігурацією, fixture та CI-результатами.

## Завдання

- використовувати `BASE_URL` для різних середовищ;
- розуміти browser projects;
- створити щонайменше одну корисну fixture або shared setup;
- читати logs, screenshots, videos і traces;
- відрізняти проблему тесту від проблеми продукту чи середовища;
- запропонувати спосіб прискорити feedback.

У цьому проєкті перевірку конфігурації можна виконати так:

```text
npm run typecheck
npm run test:chromium
npm test
```

Докази: приклад конфігурації, fixture/setup приклад і короткий опис CI troubleshooting.

### Що потрібно розуміти

Учень має пояснити, які значення залежать від середовища, чим локальний запуск відрізняється від CI та де шукати артефакти невдалого тесту. Також потрібно відрізняти проблему тесту, продукту, даних і середовища.

### Evidence package етапу 9

- приклад запуску з `BASE_URL` або іншим environment value;
- fixture/setup приклад і його призначення;
- результат локального запуску;
- короткий CI troubleshooting note: симптом, перевірки та висновок.

# Middle completion gate

Для готовності до Middle-рівня потрібно вміти:

- самостійно створювати повні сценарії;
- рефакторити код без зайвої складності;
- створювати reusable flows, helpers і fixtures;
- пояснювати вибір абстракцій;
- досліджувати та виправляти flaky behavior;
- бачити coverage gaps;
- приймати локальні рішення щодо підтримуваності та стабільності.

## Middle evidence package

- before/after refactoring;
- покращений page object або component;
- reusable helper або flow;
- fixture або shared setup;
- 3-5 самостійно спроєктованих E2E-сценаріїв;
- instability investigation з root cause і fix;
- coverage-gap proposal;
- AI-assisted workflow із перевіркою та ручними змінами;
- Git-гілка з історією змістовних комітів.

# Опціональні advanced-модулі

Ці теми не є обов'язковими для Middle-рівня:

- OCR validation;
- upload/download validation;
- network mocking;
- visual checks;
- canvas або PDF-like verification;
- accessibility checks;
- API + UI hybrid flows.

OCR слід використовувати лише тоді, коли важливий текст недоступний через DOM або API. Якщо можлива звичайна DOM-перевірка, вона зазвичай стабільніша та простіша.

# Review model

Наставник або SME оцінює п'ять напрямів:

1. **Task completion** - завдання виконане.
2. **Understanding** - учень може пояснити код.
3. **Code quality** - код читабельний і підтримуваний.
4. **Automation quality** - тести стабільні, ізольовані та змістовні.
5. **Independence** - рівень самостійності відповідає Junior або Middle.

Під час review учень повинен пояснити:

- чому обрані саме ці локатори;
- що перевіряють assertions;
- де знаходяться test data;
- навіщо потрібні fixture та page objects;
- чому виникла помилка;
- чому обраний fix є кращим за retry або hard wait.

## Як підготувати матеріали до review

Для кожного завершеного етапу можна використати короткий шаблон:

```text
Етап:
Що зроблено:
Який файл або commit це підтверджує:
Як перевірено:
Яка проблема виникла:
Чому обрано саме це рішення:
Що я тепер можу пояснити самостійно:
```

Не потрібно додавати всі логи або screenshots. Достатньо одного-двох прикладів, які підтверджують результат і розуміння.

# AI usage guidelines

AI можна використовувати як помічника для:

- пояснення TypeScript і Playwright;
- створення чернетки тесту;
- пропозиції locator або assertion;
- аналізу помилок, trace і logs;
- пошуку coverage ideas;
- рефакторингу та документації.

AI-вивід потрібно перевірити вручну. Учень повинен знати:

- що було запропоновано;
- що було прийнято;
- що було відхилено;
- що змінено вручну;
- як результат перевірено.

Приклад доказу:

```text
AI запропонував CSS locator для кнопки.
Я замінив його на getByRole(), оскільки роль і назва стабільніші.
Після цього запустив npm run typecheck і Playwright-тест.
```

### Що очікується від учня під час AI-assisted роботи

Учень має самостійно перевірити кожну пропозицію AI:

1. Порівняти її з поточною структурою проєкту.
2. Перевірити locator-и та assertions.
3. Відхилити зайву абстракцію або непотрібний hard wait.
4. Запустити typecheck і відповідні тести.
5. Пояснити, що було змінено вручну.

Коротка нотатка з prompt, перевіркою та фінальним рішенням є достатнім доказом. Сам факт використання AI не є доказом навички.

# Підсумкові результати

## Junior

Учень уміє працювати в готовій структурі Playwright-проєкту, створювати базові стабільні тести, використовувати локатори та assertions, аналізувати типові помилки й пояснювати свою реалізацію.

## Middle

Учень самостійно проєктує E2E-сценарії, покращує структуру, створює повторно використовувані компоненти, зменшує flaky behavior, аналізує coverage і аргументує технічні рішення.

## Поза межами цього посібника

- Senior-level architecture ownership;
- організаційна automation strategy;
- cross-team standardization.

# Міні-глосарій

- **Locator** - спосіб знайти елемент на сторінці.
- **Assertion** - перевірка очікуваного стану або результату.
- **Fixture** - повторно використовуваний setup або тестовий контекст.
- **Page Object** - клас, що описує сторінку, її локатори та дії.
- **Helper/Utility** - спільна технічна логіка, не прив'язана до однієї сторінки.
- **Test data** - значення, з якими працює тест.
- **Flaky test** - тест, який нестабільно проходить без змін у продукті.
- **Trace** - запис виконання тесту з діями, часом, screenshot і network-даними.
- **Isolation** - можливість запускати тест незалежно від інших тестів.
- **Reusable flow** - повторювана послідовність дій, винесена для повторного використання.
- **Abstraction** - приховування технічних деталей за зрозумілим інтерфейсом.
